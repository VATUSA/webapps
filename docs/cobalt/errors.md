# Errors

## Canonical JSON Error Envelope
Many endpoint handlers use a shared generic error response:

```json
{
  "success": false,
  "id": 0,
  "errors": ["error message"]
}
```

Generated by handler helper `GenericError(...)`.

## Canonical Success Envelope for Mutations
Some create/update/delete handlers return:

```json
{
  "success": true,
  "id": 123,
  "errors": null
}
```

`id` is usually the affected resource ID.

## Non-Canonical Error Styles
Some endpoints return errors outside the generic envelope.

### Echo HTTP Error Payloads
Used in several login/auth paths, typically shape:

```json
{
  "message": "..."
}
```

Examples:

- invalid `cid` in `GET /token/:cid`
- connect OAuth/token/user fetch failures
- disabled environment path handling (`Not found`)

### Plain Text Errors
- JWT cookie parse failure returns `401` with plain text `token error`.

### Redirect Responses
Login flow endpoints use `302 Found` redirects as expected outcomes rather than errors.

## Status Code Patterns by Endpoint Family
- News/events read: `200`, plus `400` for invalid params and `404` for missing resource where implemented.
- News/events write: `200` on success, `403` for ACL failures, `400` for invalid payload/path data, `500` for storage failures.
- User/roster reads: `200`, `400` for invalid CID, `404` for missing user, `500` for data errors.
- Login/session: mix of `200`, `302`, `401`, `403`, `404`, `500` depending on flow stage and environment gating.
- Legacy/admin: `200`, `403`, `400`, `500`.

## Troubleshooting Guide
- `403` with missing acl message: caller lacks required object/action permission.
- `401 token error`: stale or invalid `vatusa-cobalt-token` cookie.
- `404 Not found` on login helper routes: endpoint not enabled in current `APP_ENV`.
- `500` on write endpoints: often DB failure, malformed assumptions in handler, or known implementation caveat.
- Empty/unexpected response on some update paths: see [Known Issues](./known-issues.md).

## Recommendations for Integrators
- Treat all 2xx/3xx/4xx/5xx as possible and branch by status code first.
- For JSON failures, safely handle both generic envelope and Echo `message` style.
- For login flows, follow redirects and avoid assuming JSON response bodies.
